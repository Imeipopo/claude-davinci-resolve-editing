# 第 18 章　怎麼確認做對了

> 英文版：[docs/en/18-verification.md](../en/18-verification.md)
> 工具：[examples/common.py](../../examples/common.py) 的 `render()`、`Frame`、`duration()`；交片前整支檢查 [examples/tools/delivery_qa.py](../../examples/tools/delivery_qa.py)（18.7）

本教學每一條「實測通過」都用本章的方法驗證。原則只有一個：**以輸出的影片為準**。

### 18.1 為什麼不能相信回傳值

- 結論：Resolve API 的回傳值和實際效果常常不一致。本教學實測遇過的例子：

| 情況 | 回傳 | 實際 |
|---|---|---|
| 同一軌重疊放片段（4.8） | 成功 | 沒放上去 |
| Resolve FX 的影像輸入接成 `Input`（10.3） | 成功 | 輸出時才失敗 |
| `ApplyGradeFromDRX`（13.4） | 時而 `None` 時而 `True` | 兩次都套用成功 |
| 被對話框卡住時呼叫（1.5） | `None` | 什麼都沒做，也沒報錯 |
| `SetSetting("timelinePlaybackFrameRate")`（2.2） | `False` | 確實沒設，讀回仍是 24 |
| 字卡插入（6.1） | 成功 | 把底下片段切開往後推 |

- 做法：每次改完都輸出，再用下面的方法檢查。

### 18.2 截一格出來看

- 結論：用 ffmpeg 從輸出檔截出指定秒數的畫面，讓 AI 直接看圖（Claude 可以讀圖片）。
- 做法：

```bash
ffmpeg -v error -ss 3.5 -i out.mp4 -frames:v 1 frame.png
```

- 多格對照：截出關鍵時間點，拼成一張格狀圖再看，一次比對很多效果。
- 整支片一張總覽（接觸表）：平均取 24 格、排成 6×4，一行指令：

```bash
ffmpeg -v error -i out.mp4 -vf "fps=24/$(ffprobe -v error -show_entries format=duration -of csv=p=0 out.mp4),scale=480:-2,tile=6x4" -frames:v 1 sheet.jpg
```

  第 k 格（從 0 數）約在「片長 × k ÷ 24」秒。要更密就改 `24` 和 `tile`（例如 `48`、`8x6`）。
- 驗證：實測通過——15 秒的跳剪輸出與 61 秒的轉場測試片，都得到完整 24 格的 2880×1080 圖，各花 0.4 秒、0.8 秒。
- 不要：用 `ExportCurrentFrameAsStill` 截圖，它會慢一拍（2.10）。

### 18.3 用數字判斷，不靠肉眼

- 結論：把畫面解碼成像素，量「位置」和「顏色」，寫成 PASS／FAIL。肉眼看圖容易被說服，數字不會。
- 做法（`common.Frame`，不需要 numpy，ResolvePython 也能用）：

```python
f = Frame("out.mp4", 1.5)          # 解碼第 1.5 秒
f.bright_box(128)                   # 亮色區域的外框 → 量位置、大小
f.mean(600, 300, 1300, 800)         # 區域平均顏色 → 量透明度、疊圖、調色
f.diff(Frame("other.mp4", 1.5))     # 兩格平均差異 → 0 代表完全一樣
```

- 本教學用過的量法：

| 要驗證 | 素材 | 量什麼 |
|---|---|---|
| 位移、縮放、裁切單位（第 4 章） | 黑底中央 120 px 白方塊 | 白色區域的外框 |
| 透明度、疊圖模式（第 4 章） | 純色畫面 | 區域平均顏色，和公式比 |
| 轉場有沒有生效（第 5 章） | 兩段不同的畫面 | 剪接點那一格和前後兩段的差異都要 > 門檻 |
| 調色有沒有生效（第 13 章） | 照片或測試圖 | 平均 RGB 前後比較 |
| 來回匯出匯入有沒有掉東西（第 9 章） | 已加特效的時間軸 | 新舊輸出逐格 `diff` 是否為 0 |

### 18.4 自製「看得出第幾格」的測試影片

- 結論：驗證變速、時間對位時，用每一格都不一樣、而且能從畫面直接讀出格數的測試影片。
- 做法：第 N 格在 x = 2N 的位置畫一條白線（`examples/make_media.sh` 的 `ramp_src.mp4`）。輸出後量白線位置 ÷ 2，就知道這一格播的是原片第幾格。

```bash
ffmpeg -f lavfi -i "color=c=black:s=640x360:r=30:d=10" \
  -vf "format=gray,geq=lum='if(between(X,N*2,N*2+1),255,0)',format=yuv420p" ramp_src.mp4
```

- 驗證：實測通過（8.3 用它驗證變速曲線，2 倍與 0.5 倍段落一格都沒差）。

### 18.5 量長度

- 結論：`ffprobe` 量輸出長度，和時間軸應有的長度比。音訊封裝會讓檔案多出不到 0.1 秒，屬正常。
- 做法：`common.duration("out.mp4")`。

### 18.6 給使用者看的預覽

- 結論：最後一定讓人看過。AI 驗證的是「有沒有照指令做」，不是「好不好看」。
- 驗證：作者實作經驗——多次在數字全部 PASS 後，使用者仍指出「人該置中卻被切到」「白光之後應該接大圖」這類 AI 量不出來的問題。

### 18.7 交片前整支檢查：`delivery_qa.py`

- 結論：上面幾節是「這個效果有沒有做對」；交片前還要檢查「整支檔案有沒有技術問題」。`examples/tools/delivery_qa.py` 一次跑完七項，每項印 `PASS`／`WARN`／`FAIL`，有 FAIL 就回傳 exit code 1，`--json` 輸出給程式讀。只要 python3 和 ffmpeg，不需要 Resolve。
- 驗證：整理自 Hao0321（[video-autopilot-kit](https://github.com/Hao0321/video-autopilot-kit) 的交片 QA 想法），程式為本 repo 重寫，本 repo 已實測｜macOS 27.0.1／ffmpeg 8.1.2／2026-10-23。
- 做法：

```bash
python3 examples/tools/delivery_qa.py out.mp4              # 目標響度預設 -14 LUFS，--target 可改
python3 examples/tools/delivery_qa.py out.mp4 --json
```

| 檢查 | 怎麼量 | 門檻 | 門檻來源 |
|---|---|---|---|
| 響度 | `loudnorm=print_format=json` 的 `input_i` | 偏離目標 > 1 LU 為 WARN、> 5 LU 為 FAIL；整條音軌是數位靜音（-inf）為 WARN | ±1 是 Hao0321 的起始值；±5 是本 repo 依下表實測片選的（見下） |
| 真峰值 | 同上的 `input_tp` | > -1 dBTP 為 WARN、> 0 dBTP 為 FAIL（解碼後已經破音） | -1 是 Hao0321 的起始值，未驗證；0 是定義 |
| 影音長度 | ffprobe 兩條串流的 `duration` 差 | > 0.1 秒 WARN、> 0.4 秒 FAIL | 0.4 是 Hao0321 的起始值；0.1 依實測（正常輸出差 0.008～0.079 秒） |
| 結尾淡出 | 最後 0.1 秒音訊的 RMS，和「最後一秒之前的 3 秒」比 | 低於 -40 dBFS，或比前面小 20 dB 以上，才算有淡出 | 本 repo 實測：1 秒線性淡出的最後 0.1 秒是 -40.7 dBFS（前面 -16.0） |
| 死空檔 | `freezedetect=n=-60dB:d=2`（畫面靜止）**和** `silencedetect=noise=-35dB:d=2`（沒聲音）的交集 | 交集有一段 ≥ 1 秒就 FAIL；**只有畫面靜止不算** | 偵測參數是 Hao0321 的起始值（靜止長度 3 秒改成 2 秒），未驗證 |
| 長時間無聲 | `silencedetect` 的單段長度 | ≥ 5 秒 WARN（畫面在動，但聲音不見了？） | 本 repo 選的，抓到過一次 Resolve 漏掉音訊（22.5） |
| 黑畫面閃一下 | `blackdetect=d=0.02:pic_th=0.90` | 不在頭尾 0.5 秒內、短於 0.15 秒的黑畫面，而且**前後一格就是正常亮度**才 FAIL | 本 repo 實測（見下：時間軸空一格 vs. 轉場） |
| 死黑邊 | `cropdetect` 每秒取 2 格、每格獨立算 | **相對兩邊**都暗超過 16 px，連續 ≥ 1 秒 FAIL、更短 WARN | 本 repo 實測（只有一邊暗是暗場景，不算） |

- 驗證（故意做壞的測試片，各 12 秒 1920×1080，每支只壞一項）：

| 測試片 | 結果 |
|---|---|
| 正常（-14.1 LUFS、-12.7 dBTP、結尾 1 秒淡出） | 全部 PASS |
| 第 150 格 1 格黑、第 240–242 格 3 格黑 | 黑畫面 FAIL（5.00–5.03、8.00–8.10 秒），其他 PASS |
| 4–7.5 秒畫面定格**且**靜音 | 死空檔 FAIL（4.01–7.51 秒） |
| 4–7.5 秒畫面定格、音樂照放（像照片幻燈片） | 全部 PASS |
| 整支上下黑邊（2.4:1） | 死黑邊 FAIL（上下各 140 px） |
| 中間 4 秒放一張直幅圖、沒做模糊填底 | 死黑邊 FAIL（4.00–8.00 秒，左右各 656 px） |
| 音樂在最後一格硬切 | 結尾 FAIL（最後 0.1 秒 -16.0 dBFS，和前面一樣大聲） |
| 音訊比影像短 2 秒 | 影音長度 FAIL（差 2.000 秒） |
| 整體小 12 dB | 響度 FAIL（-26.1 LUFS） |
| **Resolve 時間軸故意在第 90 格留一格空白**再輸出 | 黑畫面 FAIL（3.00–3.03 秒）：時間軸上的空隙輸出出來就是一格黑 |

- 驗證（作者實際交出去的成品，唯讀檢查，各約 12～14 秒跑完，Apple M2 Max）：

| 影片 | 響度／真峰值 | 其他 |
|---|---|---|
| 4 分鐘 KTV 背景片 | -12.6 LUFS（WARN）／-1.1 dBTP | 影音差 0.071 秒、結尾 -95.3 dBFS，其餘全 PASS |
| 4 分 20 秒照片成長影片 | -10.3 LUFS（WARN）／**+0.6 dBTP（FAIL，已破音）** | 結尾 5.7 秒無聲（WARN） |
| 3 分 23 秒狗狗紀念影片 | -18.4 LUFS（WARN）／-0.2 dBTP（WARN） | 結尾 11.8 秒無聲（WARN）；最後 3 格黑畫面判為淡出 |

  三支都沒有死空檔、黑閃、黑邊誤報。響度 -18.4 與 -10.3 都是已經交出去的片，所以 FAIL 門檻放在 ±5 LU，讓它們是 WARN 而不是 FAIL；要上傳平台的話，這兩支確實該重新調響度。
- 驗證（本 repo `examples/out` 的範例輸出）：
  - 3:2 的測試圖放進 16:9 時間軸，左右各 150 px 黑邊，直幅照片 600 px，全部被抓到（範例本來就沒做填底，屬正確偵測）。
  - 第 5 章轉場測試片在 30 秒（Dip To Color Dissolve）和 40 秒（Flip 3D）各有 2 格黑。黑之前的亮度是逐格變暗（例如 101→85→70→54→39），判為轉場、不是黑閃。分辨規則：緊貼黑畫面的那一格，亮度低於再往前 3 格的 60%，就算「漸暗」。
  - 抓到兩個真問題：Fairlight 殘響測試片真峰值 +3.0 dBTP；人聲分離示範片音訊比影像短 2.096 秒。
  - 很多測試片的音軌是數位靜音，響度一律 WARN，不是錯。
- 不要：
  - 把「畫面靜止」當錯。照片幻燈片、字卡本來就會靜止，只有「靜止又沒聲音」才是死空檔。
  - 只看 `RESULT`。響度 WARN 在婚禮現場播放可能無所謂，上傳平台就要處理；由人決定。
- 仍做不到：中央跳出的通知視窗、對位歪掉、構圖切到人。這些要看 18.2 的接觸表、由人看。

> 人類補充：這支工具不是評分，是把「交出去才被發現」的低級錯誤先抓出來——破音、少一格黑畫面、音樂被硬切、直幅照片留黑邊。門檻寫在檔案最上面，自己的片子量過幾支之後可以改。
